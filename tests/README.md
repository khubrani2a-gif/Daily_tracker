# اختبارات مفكرتي اليومية · Tests

اختبارات آلية بواجهة Playwright (Chromium بلا واجهة) تُحمّل `index.html` فعليًا في المتصفّح
وتتحقّق من السلوك عبر `localStorage`/DOM وخطّافات مزامنة داخلية للقراءة فقط.

## التشغيل

```bash
# يتطلّب Playwright + Chromium. حدّد المسار إن لم تكن الحزمة مثبّتة عالميًا:
export PW_PATH=/path/to/node_modules/playwright     # اختياري
node tests/sync-contract.test.js          # عقد المزامنة (بنود المراجعة الحاجزة)
node tests/coordinator-containment.test.js # المنسّق العام + عزل الأعطال + تزامن عبر الأجهزة
node tests/fixed-expenses.test.js          # الالتزامات الثابتة + توفيق المثيلات عند التحميل
node tests/expenses-travel.test.js         # مصاريف السفر + التقارير + عدم تجاوز أفقي
node tests/startup-hardening.test.js       # إقلاع سليم رغم بيانات مصاريف مشوّهة
```

كل ملف يطبع `RESULT: N passed, M failed` وينهي برمز خروج غير صفري عند أي فشل
أو أي خطأ JS في الصفحة.

## ماذا يغطّي `sync-contract.test.js`

يغطّي بنود المراجعة الحاجزة لإصلاح v99:

1. **عقد Expenses كبقيّة الأقسام** — قراءة «الخادم أولًا ثم الكاش صراحةً»؛ عدم تخطّي الكاش
   لمجرّد انقطاع الاتصال؛ `expPushRemote` يُعيد وعدًا بنتيجة `{ok}`؛ انتظار كتابة المصالحة؛
   عدم الدفع بعد رجوعٍ للكاش؛ حالة مُهيكلة (success/cacheFallback/failed)؛ وعدم تحديث
   «وقت آخر مزامنة خادم» بعد قراءة كاش.
2. **أقفال ذات انضمام (JOIN) لكل قسم** — عند التداخل، التشغيل الأحدث ينضمّ لقراءة التشغيل
   الأقدم بدل ردّ throttled فوري: قراءة فيزيائية واحدة لكل قسم، ونتيجة الخادم الصالحة تصل
   الحالة المحلية والواجهة، وكل أعلام inFlight تعود false، والحالة العامّة لا تعلق على «جارٍ».
3. **حراسة الجيل (`_syncRunGen`)** — تُستخدم فقط لمنع كتابة حالة مرئية متقادمة، ولا تُسقط أبدًا
   بيانات خادم صالحة؛ الأقدم ليس الأحدث فلا يكتب الحالة المرئية.
4. **محاسبة فشل كتابة المصالحة** (Daily وExpenses) — بعد فشل الكتابة: الحالة `failed`،
   و`lastError==="reconWriteFailed"`، و`lastServerSuccessAt` لا يتقدّم، وفي Expenses
   `lastSyncAt` المرئي لا يتقدّم، والملخّص العام ليس `ok`.
5. **تصليب الإنتاج** — الطرائق المُحدِثة للكتابة (`pullAll`/`expPull`/`expPush`) لا تظهر إلّا مع
   العلم `window.__MFKR_TEST__=true`؛ في الإنتاج يبقى التشخيص للقراءة فقط.

الاختبار يُفعّل العلم عبر `addInitScript(()=>{ window.__MFKR_TEST__=true; })` قبل التحميل.

## الهرمِتيّة (Hermeticity) — اعتراض شبكة Firebase

يحمّل `index.html` سكربتات Firebase compat من الشبكة:
`https://www.gstatic.com/firebasejs/10.14.1/firebase-{app,auth,firestore}-compat.js`.
هذه تُنفَّذ **بعد** حقن البديل (`addInitScript`) فتستبدل `window.firebase` الحقيقية لو توفّر الإنترنت،
فتفقد الاختبارات هرمِتيّتها.

لذلك **تعترض** المجموعتان القائمتان على البديل (`sync-contract`, `coordinator-containment`) — عبر
`page.route("https://www.gstatic.com/firebasejs/**", r=> r.abort())` قبل كل `goto` — وتُجهضان تحميل
سكربتات Firebase من CDN عمدًا، فيبقى البديل المحقون هو المُسيطر. يحمل البديل علامةً صريحة
`firebase.__MFKR_FAKE__ = true`، وبعد كل تحميل يؤكّد الاختبار بقاءها (`fake Firebase authoritative
after load …`) فيفشل بوضوح لو استبدلت الحقيقيةُ البديلَ. يُطبَّق هذا على كل صفحة/سياق، بما فيها
صفحة اختبار خطّاف الإنتاج. لذا تمرّ المجموعتان سواءٌ توفّر الإنترنت أم لا.

## حدود صادقة (Honest limitations)

- هذه **ليست** محاكاة Firestore حقيقية ولا ثلاثة عملاء فيزيائيين. تستخدم بديلًا
  في‑الذاكرة أمينًا لواجهة compat يميّز `{source:"server"}` عن `{source:"cache"}`،
  ويحقن أعطال الخادم/الكتابة والتأخير وعدّاد الكتابات. التقارب «عبر الأجهزة» مُحاكى
  عند حدّ الواجهة (نفس متجر الذاكرة بين سياقات المتصفّح)، لا عبر الشبكة.
- التحقّق النهائي على أجهزة حقيقية (استئناف التطبيق بعد نوم الخلفية، كاش IndexedDB فعلي)
  يبقى خطوة يدوية خارج نطاق هذه المجموعة.
