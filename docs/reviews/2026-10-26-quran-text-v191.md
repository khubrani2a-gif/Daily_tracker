# Quran typography and custom qiyam range

The old reader used Thmanyah Sans, an interface font. Comparing its cmap with the actual AlQuran.cloud quran-uthmani Surah 66 response found missing U+0671, U+06D6, U+06DA, U+06DF, U+06E2, U+06E5, U+06E6, U+06ED. Browser fallback can disrupt the appearance and placement of these glyphs. This confirms a font coverage defect; it does not establish that every apparent difference from modern Arabic spelling is incorrect Quran text.

Bundled Amiri Quran from https://github.com/google/fonts/tree/main/ofl/amiriquran (OFL license included). Its cmap covers every visible codepoint in the full AlQuran.cloud quran-uthmani response (114 surahs, 6236 ayahs); U+FEFF is a zero-width formatting character, not a visible letter. Font conversion TTF to WOFF2 uses fontTools without text changes. Font loading failure prevents reader display and offers the existing Quran.com range link.

The Quran text is never generated or manually rewritten. Basmala is separated only when the exact source prefix is present on verse 1 outside Al-Fatiha/At-Tawbah, preserving its original characters. Old cache entries are refreshed. Empty, duplicate or missing requested verses fail closed. These structural checks do not constitute independent scholarly authentication of the entire external dataset.

Custom selection: surah, first ayah, last ayah, count preview. Invalid bounds and stale plans are rejected. Previously recorded readings are preserved. The existing confirmed reading/undo flows are reused; selecting a plan never records prayer.

Tests: regression cases first reproduced legacy cache acceptance, silently omitted verses, malformed rows and missing custom range validation. Browser cases cover source text equality, loaded Quran font, basmala, partial range reading and undo, stale form and failed font. Surah66 fixture is a verbatim response fetched 2026-10-26 from https://api.alquran.cloud/v1/surah/66/quran-uthmani. Local browser execution is blocked by host thread exhaustion; CI must pass before merge.
